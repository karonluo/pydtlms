# 完成博士生招生环节开发计划

## 1. 背景

根据当前确认的博士生招生业务口径，整体流程共 6 个环节：

1. 在线申请
2. 资料审核
3. 背景评估
4. 中心考核
5. 结果公布
6. 预录取

其中，第 1 个环节“在线申请”下包含 8 个申报章节：

1. 基本信息
2. 报名信息
3. 教育经历
4. 实践经历
5. 英语能力
6. 家庭情况
7. 成果经历
8. 个人陈述

按当前项目进展，前 2 个环节已完成，后续待完成环节为：

1. 背景评估
2. 中心考核
3. 结果公布
4. 预录取

本计划用于收敛后续开发范围、实施顺序、数据库变更归口与联调验收标准。

## 2. 当前范围确认

### 2.1 已完成环节

1. 在线申请
   - 学生门户在线申请按 8 个章节组织。
   - 章节完成情况已支持展示。
   - 学生门户首页已具备招生环节状态展示基础。
2. 资料审核
   - 已支持资料提交后的审核处理。
   - 已具备通过、驳回重填等基础流转能力。

### 2.2 待完成环节

1. 背景评估
2. 中心考核
3. 结果公布
4. 预录取

### 2.3 设计约束

1. 数据库为唯一事实来源，正式业务数据不能只存在内存态或前端态。
2. 如需新增字段、关系、索引或持久化结构，必须同步追加到 [backend/sql/update20260521.sql](backend/sql/update20260521.sql)。
3. 已有流程托管对象应优先沿用现有 workflow 能力，避免并行造第二套状态机。
4. 前后端展示口径必须统一，尤其是“申请流转状态”“报名状态”“结果公布结果”。
5. 学生侧与系统角色侧沿用当前已分离的现状即可，本轮不新增额外角色体系设计。

## 3. 目标

1. 完成博士生招生后续 4 个环节的系统闭环。
2. 保证学生门户、招生工作台、审批中心、邮件通知之间的状态一致。
3. 在沿用现有学生体系与系统角色体系分离现状的前提下，明确书院管理员、导师等管理侧职责边界。
4. 保证每个环节都有清晰的进入条件、处理动作、分支规则、完成条件。
5. 在上线前形成可执行的 SQL、测试、联调和发布清单。

## 4. 后续环节开发计划

## 4.1 环节三：背景评估

### 4.1.1 业务理解

1. 资料审核通过后，申请进入“背景评估”环节。
2. 当前状态口径：
   - 申请流转状态：待背景评估
   - 报名状态：已填写报名
3. 背景评估由书院管理员处理。
4. 该环节不是单人审批，而是多位书院管理员参与、达到阈值后汇总决策的环节。
5. 书院管理员在实际业务中不少于 3 位，因此系统需要支持第 3 位及以上管理员继续参与评估。
6. 每位评估人必须是不同的书院管理员，不能由同一人重复提交多次替代多人评估。
7. 每位书院管理员提交的内容至少包含：评估结论、评估意见、评估时间。
8. 背景评估完成后，只产生两类正式结果：进入中心考核，或报名终止。

### 4.1.2 需要完成的功能

1. 增加背景评估节点与相应状态流转规则。
2. 增加背景评估记录结构，保存每位书院管理员的评估结论、意见、时间。
3. 实现双人评估汇总规则：
   - 2 位书院管理员评估通过，进入“中心考核”
   - 2 位书院管理员评估不通过，报名终止
4. 在审批详情或招生工作台详情中展示背景评估明细。
5. 发送邮件通知：
   - 通过：通知进入中心考核
   - 不通过：通知报名终止
6. 学生门户首页同步显示当前环节和结果。

### 4.1.2.1 建议冻结的精确汇总规则

1. 同一申请在背景评估环节下，允许多位书院管理员依次提交评估记录，但每位书院管理员仅保留 1 条有效评估记录。
2. 若允许修改，应覆盖本人此前记录，不新增第二条有效记录。
3. 当“通过”累计达到 2 票时：
   - 背景评估汇总结果为“通过”
   - 申请立即流转到“待中心考核”
   - 后续不再继续收集新的背景评估结果
4. 当“不通过”累计达到 2 票时：
   - 背景评估汇总结果为“不通过”
   - 申请立即流转到“报名终止”
   - 后续不再继续收集新的背景评估结果
5. 在“通过”未满 2 票且“不通过”未满 2 票之前，申请流转状态始终保持“待背景评估”。
6. 因书院管理员不少于 3 位，出现“1 通过 + 1 不通过”时不视为异常或冲突场景，而是继续等待下一位书院管理员提交评估，直到满足“2 票通过”或“2 票不通过”的终局条件。
7. 一旦达到终局条件，背景评估环节关闭，后续管理员不能再对该申请提交新的背景评估结果。

### 4.1.2.2 建议冻结的数据字段

建议分为“评估明细字段”和“汇总结果字段”两层。

评估明细字段：

1. application_id 或 recruitment_application_id
2. business_key 或 candidate_no
3. evaluator_user_id
4. evaluator_username
5. evaluator_name
6. evaluator_role_code
7. evaluation_result
8. evaluation_comment
9. evaluated_at
10. created_at
11. updated_at

汇总结果字段：

1. background_assessment_status
2. background_assessment_pass_count
3. background_assessment_reject_count
4. background_assessment_decision
5. background_assessment_completed_at
6. background_assessment_closed_flag
7. background_assessment_closed_by_user_id

字段说明建议：

1. evaluation_result 取值建议冻结为：通过、不通过。
2. background_assessment_status 用于表示当前环节处理态，建议区分：待评估、评估完成。
3. background_assessment_decision 用于表示最终业务结论，建议区分：通过、不通过、未决。
4. background_assessment_closed_flag 用于标记背景评估是否已达到终局条件并关闭。
5. background_assessment_closed_by_user_id 用于记录触发终局条件的最后一位评估人。

### 4.1.3 技术落点

1. 后端：
   - workflow 节点定义与动作处理
   - 背景评估持久化结构
   - 状态汇总逻辑
   - 邮件通知与操作日志
2. 前端：
   - 招生工作台详情页/操作区展示背景评估信息
   - 审批中心动作与结果展示
   - 学生门户首页状态回显
3. 数据库：
   - 本环节涉及的表结构或字段调整统一追加到 [backend/sql/update20260521.sql](backend/sql/update20260521.sql)

### 4.1.4 验收标准

1. 单个书院管理员提交结果后，不自动推进到下一环节。
2. 达到双人通过条件后，申请才能进入“待中心考核”。
3. 达到终止条件后，申请流转状态更新为“报名终止”。
4. 学生可在门户端看到正确的当前环节与状态结果。

## 4.2 环节四：中心考核

### 4.2.1 业务理解

1. 背景评估通过后进入中心考核。
2. 当前状态口径：
   - 申请流转状态：待中心考核
   - 报名状态：第一志愿考核 或 第二志愿考核
3. 中心考核不再按“研究中心负责人”处理，而是由学生填报志愿时所选择的导师处理。
4. 第一志愿和第二志愿必须严格区分，分别由对应志愿所选导师进行考核。
5. 导师在考核时需要填写分数，并提交考核结论：通过或不通过。
6. 若第一志愿不合格且存在第二志愿，则自动流转至第二志愿考核，并由第二志愿所选导师继续处理。

### 4.2.2 需要完成的功能

1. 增加第一志愿考核、第二志愿考核的流程分支控制。
2. 支持按志愿关联对应导师，确保只有学生所选导师可以处理本轮考核。
3. 支持导师提交考核分数、考核意见和“通过/不通过”结论。
4. 单志愿场景下：
   - 合格：进入结果公布
   - 不合格：结束报名并进入结果公布控制链路
5. 双志愿场景下：
   - 第一志愿不合格且存在第二志愿，自动转入第二志愿考核
   - 第二志愿合格，进入结果公布
   - 第二志愿不合格，结束报名并进入结果公布控制链路
6. 发送邮件通知：
   - 待第二志愿考核
   - 考核通过
   - 考核不通过
7. 在管理端和流程详情中展示当前考核志愿、对应导师、考核分数、考核意见和考核结论。

### 4.2.3 技术落点

1. 后端：
   - workflow 分支规则
   - 志愿顺序与对应导师校验
   - 考核分数、考核意见、考核结论持久化
   - 状态回写和邮件通知
2. 前端：
   - 招生工作台展示当前考核志愿与对应导师
   - 中心考核动作入口支持填写分数、意见和通过/不通过
   - 学生门户首页显示考核结果走向
3. 数据库：
   - 若需新增考核记录表、导师关联字段、分数字段、考核意见字段或结果字段，统一进入 [backend/sql/update20260521.sql](backend/sql/update20260521.sql)

### 4.2.4 验收标准

1. 单志愿与双志愿场景均能正确闭环。
2. 第一志愿不通过时，第二志愿流转条件准确。
3. 报名状态能准确区分“第一志愿考核”和“第二志愿考核”。
4. 只有对应志愿所选导师才能提交本轮中心考核结果。
5. 每一轮中心考核都能完整记录分数、意见和通过/不通过结论。
6. 邮件通知内容与学生实际所处状态一致。

## 4.3 环节五：结果公布

### 4.3.1 业务理解

1. 中心考核结果不能直接对学生发布。
2. 最终结果需要由导师提交，再由书院管理员审核后，才发布到学生门户前端。
3. 学生门户最终看到的结果包括：
   - 第一志愿考核通过
   - 第二志愿考核通过
   - 不合格
4. 结果公布所依据的最终结果，应来自对应志愿导师提交的中心考核分数和通过/不通过结论。

### 4.3.2 需要完成的功能

1. 新增“结果公布”业务节点。
2. 提供导师提交结果入口。
3. 提供书院管理员审核发布入口。
4. 结果审核通过前，学生门户不得提前显示最终结果。
5. 发布完成后，在学生门户首页和相关详情中同步展示结果。
6. 增加结果发布日志和邮件通知。

### 4.3.3 技术落点

1. 后端：
   - 结果公布节点与动作定义
   - 导师提交、书院审核、学生端发布状态联动
   - 结果持久化与日志留痕
2. 前端：
   - 导师侧结果提交入口
   - 书院管理员审核入口
   - 学生门户结果展示
3. 数据库：
   - 若需新增结果草稿、审核意见、发布时间等字段，统一进入 [backend/sql/update20260521.sql](backend/sql/update20260521.sql)

### 4.3.4 验收标准

1. 中心考核完成后，学生端不会越权提前看到最终结果。
2. 导师提交后，书院管理员可审核发布。
3. 发布完成后，学生门户展示结果与考核分支一致。

## 4.4 环节六：预录取

### 4.4.1 业务理解

1. 结果公布审核完成后，学生才可进入预录取处理。
2. 学生点击“接受录取”前，需要先看到通知声明。
3. 通知声明弹框倒计时 10 秒后，学生方可确认接受预录取。
4. 接受后可下载预录取通知书，并触发邮件通知。

### 4.4.2 需要完成的功能

1. 新增预录取节点与状态流转。
2. 增加预录取声明弹框。
3. 支持 10 秒倒计时控制后再允许点击“接受预录取”。
4. 支持接受预录取后的状态回写。
5. 支持预录取通知书下载。
6. 增加邮件通知与操作日志。

### 4.4.3 技术落点

1. 后端：
   - 预录取状态持久化
   - 通知书下载接口或文件生成逻辑
   - 邮件通知与日志
2. 前端：
   - 弹框、倒计时、确认交互
   - 通知书下载入口
   - 学生门户状态回显
3. 数据库：
   - 若需新增预录取确认时间、通知书路径、声明确认记录，统一进入 [backend/sql/update20260521.sql](backend/sql/update20260521.sql)

### 4.4.4 验收标准

1. 倒计时结束前，学生不能点击接受预录取。
2. 接受成功后，状态回写准确。
3. 预录取通知书可正常下载。
4. 邮件通知与门户展示一致。

## 5. 建议实施顺序

建议按以下顺序推进：

1. 背景评估
2. 中心考核
3. 结果公布
4. 预录取

原因如下：

1. 背景评估是资料审核后的直接下一环节，且存在双人评估规则，优先实现可避免后续返工。
2. 中心考核依赖背景评估通过后的流转结果。
3. 结果公布依赖中心考核结论，不宜提前脱离考核链单独实现。
4. 预录取依赖结果公布完成后才可进入，天然位于最后阶段。

## 6. 每阶段交付要求

每个环节开发完成后，应至少同步交付以下内容：

1. 后端接口与状态流转实现。
2. 前端页面或操作入口改造。
3. 单元测试或关键流程测试。
4. 数据库 SQL 变更脚本，统一追加到 [backend/sql/update20260521.sql](backend/sql/update20260521.sql)。
5. 操作日志与邮件通知联调验证。

## 7. 联调与上线准备

在四个待完成环节全部开发完成后，统一进行以下工作：

1. 端到端联调：
   - 资料审核通过 -> 背景评估通过 -> 中心考核 -> 结果公布 -> 预录取
   - 资料审核通过 -> 背景评估不通过
   - 第一志愿不通过 -> 第二志愿考核
   - 第二志愿不通过 -> 结果公布为不合格
2. 补齐门户首页流程状态与实际 workflow 状态映射验证。
3. 补齐邮件通知文案和触发时机验证。
4. 复核所有数据库变更均已落入 [backend/sql/update20260521.sql](backend/sql/update20260521.sql)。
5. 输出发布步骤、回滚预案和生产验证清单。

## 8. 结论

当前博士生招生流程中，前 2 个环节已完成，后续开发重点为：背景评估、中心考核、结果公布、预录取。

后续所有实现应围绕“状态一致、权限清晰、邮件联动、门户可见、数据库留痕”五个原则推进，并统一将本轮数据库变更汇总到 [backend/sql/update20260521.sql](backend/sql/update20260521.sql)。
