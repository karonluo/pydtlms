## 1. 背景

【导师初筛】当前需要新增一个独立的【已提交】标签页，用于展示导师已提交的初筛学生记录。

本次需求的核心要求是：

1. 必须新建一个专用后端服务代码文件，不复用以前的界面逻辑。
2. 必须新建一个独立前端页面文件，不复用以前的界面文件。
3. 后端查询逻辑以 `backend\sql\导师初筛已提交学生SQL脚本.sql` 为准，并在此基础上补齐分页 SQL 与查询 SQL。
4. 前端仅负责该标签页的列表展示、查询与分页，查询关键字仅支持报名号和学生姓名。
5. 页面风格可以参考既有页面，但实现必须是新文件、新页面、新服务。

## 2. 目标

1. 实现【导师初筛 -> 已提交】标签页的独立列表查询能力。
2. 实现【导师初筛 -> 已提交】标签页的独立页面展示能力。
3. 支持关键字查询、分页查询与列表结果展示。
4. 保持该标签页与既有导师初筛页面在风格上统一，但代码层面完全独立。
5. 完成后端、前端、接口与文档的最小闭环。

## 3. 当前冻结的需求理解

### 3.1 功能边界

【已提交】标签只做已提交导师初筛学生的查询展示，不承担以下职责：

1. 不做打分提交。
2. 不做签名提交。
3. 不做导师初筛的录分操作。
4. 不做初筛确认操作。
5. 不复用旧页面中的交互组件来承载本标签核心实现。

### 3.2 查询范围

1. 只查询【导师初筛】场景下已提交的数据。
2. 列表支持分页。
3. 关键字只支持：
   - 报名号
   - 学生姓名

### 3.3 文件约束

1. 后端必须新增专用服务文件。
2. 前端必须新增专用页面文件。
3. 允许参考既有页面样式与布局，但不得直接沿用旧页面文件承载该标签。

## 4. 当前现状判断

### 4.1 已有基础

1. 现有【导师初筛】页面已经具备列表、签名和提交相关的通用样式参考。
2. 现有后端已经存在招生/报名/初筛相关查询能力，可作为字段与分页实现参考。
3. 现有 SQL 脚本中已经存在“已提交学生”的基础查询语义，可继续扩展为分页版本。

### 4.2 当前缺口

1. 缺少一个专用于【已提交】标签的后端服务文件。
2. 缺少一个专用于【已提交】标签的前端页面文件。
3. 缺少该标签对应的分页查询 SQL。
4. 缺少该标签对应的查询参数收口与返回模型收口。
5. 缺少独立页面的路由与标签接入。

## 5. 范围说明

本轮只做以下内容：

1. 新建【导师初筛 -> 已提交】的后端服务文件。
2. 新建【导师初筛 -> 已提交】的前端页面文件。
3. 将 `backend\sql\导师初筛已提交学生SQL脚本.sql` 扩展为可分页、可查询的正式 SQL。
4. 接入页面标签、路由与接口。
5. 补充验证与文档。

本轮不做以下内容：

1. 不改导师初筛现有已提交/待提交以外的功能逻辑。
2. 不扩展查询关键字到更多字段。
3. 不把该标签并入旧页面文件中实现。
4. 不修改与该标签无关的招生流程、审批流程和学生端口径。

## 6. 开发步骤

### 第 1 步：冻结查询口径与返回字段

怎么做：

1. 先确认【已提交】标签需要展示的字段集合。
2. 明确分页所需的入参、排序规则、关键字匹配规则。
3. 对 `backend\sql\导师初筛已提交学生SQL脚本.sql` 做分页化改造，保证查询结果与页面字段一一对应。

本步骤冻结后的查询口径：

1. 仅查询当前登录导师名下的已提交记录。
2. 命中条件以志愿导师匹配为准：第一志愿导师或第二志愿导师为当前登录导师。
3. 已提交判定以对应志愿的筛选提交时间不为空为准。
4. 关键字只支持报名号和学生姓名，均采用模糊匹配。
5. 当前步骤先不扩展到其他筛选字段，不加更多业务搜索条件。
6. 无需增加 `advisor_screening_status` 条件。
7. 需要保留 `plan_id` 字段，后续页面和服务均按计划维度展示与筛选。

本步骤冻结后的返回字段：

1. student_id
2. candidate_no
3. business_key
4. full_name
5. application_id
6. first_choice_screening_submitted_at
7. second_choice_screening_submitted_at
8. first_choice
9. first_choice_id
10. second_choice
11. second_choice_id
12. choice_score
13. choice_name

待确认点：

1. 已确认不需要在已提交判定之外，再额外加上 advisor_screening_status = submitted 作为双重约束。
2. `ra.candidate_no` 即报名号，后续后端字段命名和页面展示都以此为准。
3. `plan_id` 需要一并保留，作为页面和服务的计划维度字段。

为什么这样做：

1. 先冻结 SQL 与字段，后续后端服务和前端页面才能保持一致。

确认点：

1. 你确认【已提交】标签的查询字段、排序与分页口径后，再进入后端文件创建。

3. 由于要求必须新建文件，后续改动要避免回到旧页面中做补丁式实现。
