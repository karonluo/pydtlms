### 2026-06-16 需求说明

当前用户已明确冻结以下口径：

1. 不再依赖 `dtlms_advisors` 这张表处理研究中心。
2. 研究中心的数据维护只围绕 `dtlms_teams`、`dtlms_team_advisors`、`dtlms_users` 三张表展开。
3. 新增和编辑研究中心时，负责人/成员应从导师角色用户中选择。
4. 保存时只处理这三张表之间的关系，不再关心其他派生表或旧链路数据。
5. 以上功能需要新增一个后端服务代码文件，集中承接 CRUD 与建联逻辑。

## 1. 背景

现有研究中心链路仍然混用了旧的导师主数据表与研究中心关系表，导致读写口径分散、依赖面过大，也不符合当前“只围绕三表建联”的新要求。用户已经明确要求：研究中心管理从现在开始不再依赖 `dtlms_advisors`，而是直接从导师角色用户中选人，并通过 `dtlms_teams` 与 `dtlms_team_advisors` 保存关系。

本计划用于冻结新口径、梳理影响面、规划实现顺序，并作为后续开发与回归的唯一执行基线。

## 2. 目标

1. 新增一个专用后端服务文件，集中处理研究中心 CRUD、负责人/成员建联、关系同步与必要校验。
2. 研究中心读写链路全面切换为 `dtlms_teams`、`dtlms_team_advisors`、`dtlms_users`。
3. 负责人/成员候选项统一来源于导师角色用户，而不是 `dtlms_advisors`。
4. `/students/centers` 接口与前端页面保持功能可用，但内部实现改为新服务驱动。
5. 不扩展到其他与研究中心无关的模块，避免引入额外改动面。
6. 同步更新必要的测试、文档与上线说明，保证口径一致。

## 3. 当前冻结的需求理解

### 3.1 数据口径

研究中心管理只维护以下对象：

1. `dtlms_teams`：研究中心主记录。
2. `dtlms_team_advisors`：研究中心与导师角色用户的关系记录。
3. `dtlms_users`：导师角色用户主数据来源。

明确不再把 `dtlms_advisors` 作为研究中心 CRUD 的主依据，也不再要求保存流程去同步它。

### 3.2 人员选择口径

新增/编辑研究中心时：

1. 负责人从导师角色用户中选择。
2. 成员从导师角色用户中选择。
3. 候选列表应能明确体现导师身份、姓名与必要标识，便于前端区分。
4. 用户是否属于导师角色，应由 `dtlms_users` 关联角色表判断，不依赖旧导师表。

### 3.3 CRUD 与建联口径

保存研究中心时：

1. 先写或更新 `dtlms_teams`。
2. 再按当前表单选择同步 `dtlms_team_advisors`。
3. 关系写入只围绕负责人/成员建联，不额外联动旧表。
4. 编辑时需要保证关系幂等，避免重复关系或残留旧关系。
5. 删除时只处理当前研究中心对应的主记录与关系记录。

### 3.4 页面与接口口径

1. 现有 `/students/centers` 页面继续作为入口。
2. 前端新增/编辑弹窗的选人控件改为导师角色用户列表。
3. 列表页展示口径以新服务返回为准。
4. 页面上不再出现依赖 `dtlms_advisors` 的选择来源或展示字段。

### 3.5 页面影响面冻结

本轮只冻结与研究中心页直接相关的页面和接口链路，影响面限定如下：

1. 后端接口入口：[backend/app/api/v1/students.py](../backend/app/api/v1/students.py)
2. 后端学生/中心服务层：[backend/app/services/management_service_students.py](../backend/app/services/management_service_students.py)
3. 后端中心查询层：[backend/app/services/postgres_state_store_query_students.py](../backend/app/services/postgres_state_store_query_students.py)
4. 后端中心数据模型：[backend/app/schemas/student.py](../backend/app/schemas/student.py)
5. 前端中心 API：[frontend/src/api/students.ts](../frontend/src/api/students.ts)
6. 前端研究中心页面：[frontend/src/views/students/StudentsView.vue](../frontend/src/views/students/StudentsView.vue)
7. 前端路由与菜单入口：[frontend/src/router/index.ts](../frontend/src/router/index.ts)、[frontend/src/router/menuAccess.ts](../frontend/src/router/menuAccess.ts)

冻结结论如下：

1. 本轮优先只改研究中心 section，不扩展到注册学生、门户、招生或系统治理其他页面。
2. 前端页面结构可以保留，重点只切换负责人/成员来源和保存链路。
3. 如果后续发现研究中心依赖还散落在其他文件，先记录到后续任务，不在任务1里展开修补。

### 3.6 现有读写链路结论

当前研究中心链路已经可以明确拆成“接口层 -> 服务层 -> 查询层 -> 数据库”四段：

1. 接口层入口是 [backend/app/api/v1/students.py](../backend/app/api/v1/students.py)，提供 `/students/centers`、`/students/teams`、`/students/centers/{id}`、`/students/centers/batch-delete` 等路径。
2. 服务层入口是 [backend/app/services/management_service_students.py](../backend/app/services/management_service_students.py)，其中 `get_centers`、`create_center`、`update_center`、`delete_center`、`delete_centers` 是当前中心读写主方法。
3. 查询层入口是 [backend/app/services/postgres_state_store_query_students.py](../backend/app/services/postgres_state_store_query_students.py)，其中 `list_centers_page` 是当前中心列表查询的核心实现。
4. 数据模型入口是 [backend/app/schemas/student.py](../backend/app/schemas/student.py)，其中 `CenterRecord`、`CenterUpsert`、`StudentOptionsResponse.center_advisor_map` 直接约束了前后端字段形状。
5. 前端入口是 [frontend/src/api/students.ts](../frontend/src/api/students.ts) 与 [frontend/src/views/students/StudentsView.vue](../frontend/src/views/students/StudentsView.vue)，中心页当前直接消费 `director_name`、`director_id`、`advisor_names`、`advisor_ids` 等字段。

旧表使用点已明确：

1. `dtlms_advisors` 仍出现在中心列表查询中的负责人、关键词和作用域过滤逻辑里。
2. `dtlms_team_advisors` 仍承担中心成员关系的查询与展示。
3. `dtlms_users` 目前主要用于作用域过滤和导师角色识别，但尚未成为中心候选人的唯一来源。

字段依赖已明确：

1. 前端表单仍依赖 `director_name`、`director_id`、`advisor_names`、`advisor_ids`、`advisor_relation_ids`。
2. 后端中心记录返回仍包含 `created_date`、`is_enabled`、`member_student_count`、`active_student_count` 等展示字段。
3. `StudentOptionsResponse.center_advisor_map` 说明当前页面还存在按中心映射导师选项的旧口径。

结论：

1. 当前研究中心链路的最大问题不是页面本身，而是中心数据读写仍同时依赖旧导师表与关系表。
2. 下一阶段改造需要先把后端中心服务从学生通用服务中拆出来，再切换前端选人来源。
3. 目前已确认的旧表使用点就是本轮需要优先收口的改造入口。
