## 开发状态

- [已完成] 第一阶段-任务2：补齐重新评分所需的后端状态判断、回退条件与错误提示口径
- [已完成] 第二阶段-任务1：为【已提交】列表新增【重新评分】操作入口
- [已完成] 第二阶段-任务2：打通从【已提交】回退到【导师初筛】的状态流转
- [已完成] 第三阶段-任务1：补充接口测试、前端交互验证与构建检查
- [已完成] 第三阶段-任务2：同步更新相关需求文档、开发说明与上线材料

## 1. 背景

【导师初筛】的【已提交】列表已经具备展示、查询、分页、查看详情、志愿、分数和结论等能力。现需要在【已提交】列表中新增【重新评分】能力，用于导师对已提交记录进行回退重评分处理。

本次需求的核心要求是：

1. 【已提交】列表中的【查看】列改为【操作】列。
2. 在【操作】列中新增【重新评分】动作。
3. 点击【重新评分】后，系统先判断该学生是否已经进入【初筛确认】环节，或者是否已经进入【报名终止】环节。
4. 如果该学生已经进入【初筛确认】环节，或者已经进入【报名终止】环节，则允许在满足志愿提交条件时回退到【导师初筛】环节，重新进入可评分状态。
5. 如果该学生已经到了【面试阶段】，则不允许重新评分，并提示：因为该学生已经到了面试阶段所以无法重新评分。
6. 本次变更只围绕【已提交】列表的重评分入口与状态回退，不扩展到其他招生页面。

## 2. 目标

1. 在【导师初筛 -> 已提交】列表中提供明确的【重新评分】操作入口。
2. 将重新评分动作与既有状态流转规则对齐，保证只能在允许的业务阶段执行。
3. 对不允许的阶段给出明确错误提示，避免用户误操作。
4. 保持【已提交】列表原有的查询、分页、查看详情、志愿、分数、结论展示不受影响。
5. 完成后端判断、接口接入、前端交互与文档同步的最小闭环。

## 3. 当前冻结的需求理解

### 3.1 功能边界

【重新评分】只作用于【导师初筛 -> 已提交】列表中的单条记录，不承担以下职责：

1. 不修改【待提交】列表的提交逻辑。
2. 不修改初筛确认页面的正常确认逻辑。
3. 不修改面试阶段的业务流转逻辑。
4. 不新增批量重新评分。
5. 不改变已提交列表现有查询字段、分页逻辑和详情查看逻辑。

### 3.2 判定规则

1. 点击【重新评分】后，先判断目标学生是否已进入【初筛确认】环节。
2. 若已进入【初筛确认】环节，或者已进入【报名终止】环节，则允许回退到【导师初筛】环节。
3. 第一志愿导师的重新评分规则：必须存在第一志愿提交时间戳；如果第二志愿导师还没有提交，则允许在【初筛确认】或【报名终止】时重新评分；如果第二志愿导师已经提交，则不允许第一志愿重新评分。
4. 如果没有第二志愿导师，则第一志愿导师必须存在 `first_choice_screening_submitted_at`，并且只能在【初筛确认】或【报名终止】时允许重新评分。
5. 第二志愿导师必须存在 `second_choice_screening_submitted_at`，并且只能在【初筛确认】或【报名终止】时允许重新评分。
6. 若已进入【面试阶段】或更后续阶段，则禁止回退。
7. 禁止时的提示文案统一为：因为该学生已经到了面试阶段所以无法重新评分。
8. 回退成功后，该学生应重新回到【导师初筛】可评分状态，允许导师再次录分并提交。

### 3.3 文件约束

1. 后端优先在现有招生/初筛相关服务链路中增加重新评分判断与回退能力，避免重复造轮子。
2. 前端优先在现有【已提交】列表页面中增加操作列动作，不额外拆分独立页面。
3. 页面已有的【志愿】【分数】【结论】【提交时间】【查看详情】展示保持不变。

## 4. 当前现状判断

### 4.1 已有基础

1. 【已提交】列表已经接入到导师初筛工作台。
2. 【已提交】列表已经具备关键字查询、分页、查看详情、志愿、分数和结论展示。
3. 后端已经存在【已提交】数据查询与导师身份过滤逻辑，可作为操作入口的基础。
4. 现有初筛确认相关服务和状态字段可作为回退判定参考。

### 4.2 当前缺口

1. 缺少【重新评分】动作对应的后端业务判断入口。
2. 缺少从【已提交】回退到【导师初筛】的明确状态更新路径。
3. 缺少对【初筛确认】与【面试阶段】的操作可用性判断。
4. 缺少前端【操作】列中新的【重新评分】交互。
5. 缺少对应的接口测试与回退场景验证。

## 5. 范围说明

本轮只做以下内容：

1. 在【已提交】列表中新增【操作】列。

3. 新增后端阶段判断与回退处理。
4. 新增失败提示文案与前端交互。
5. 补充验证与文档。

本轮不做以下内容：

1. 不重构【已提交】列表的查询与分页逻辑。

3. 不修改面试阶段的业务规则。
4. 不扩展到批量重新评分。
5. 不改动与该需求无关的招生流程页面。

## 6. 开发步骤

### 第 1 步：冻结重新评分边界与判定口径

怎么做：

1. 确认【重新评分】只针对【导师初筛 -> 已提交】单条记录。
2. 明确第一志愿导师与第二志愿导师的不同重新评分窗口。
3. 明确允许回退的前置条件为：第一志愿导师在第二志愿尚未提交时，或者双方都已进入【初筛确认】环节。
4. 明确禁止回退的条件为：第二志愿导师已提交后第一志愿导师再次重新评分、或任一阶段已进入【面试阶段】。
5. 明确失败提示文案与成功后的目标状态。

本步骤冻结后的判定口径：

1. 入口来自【已提交】列表的【操作】列。
2. 判定优先级以业务阶段为准，先判断是否允许回退，再执行状态变更。
3. 第一志愿导师：在第二志愿导师尚未提交时，可重新评分；一旦第二志愿导师已经提交，则不允许再重新评分。
4. 没有第二志愿导师时，第一志愿导师必须有第一志愿提交时间戳，并且只能在【初筛确认】或【报名终止】环节重新评分。
5. 第二志愿导师必须有第二志愿提交时间戳，并且只能在【初筛确认】或【报名终止】环节重新评分。
6. 仅允许把记录从【已提交】回退到【导师初筛】。
7. 禁止跨阶段回退到其他业务阶段。

本步骤最终冻结结果：

1. 第一志愿导师在第二志愿导师未提交时可重新评分。
2. 第一志愿导师在第二志愿导师已提交后禁止重新评分。
3. 没有第二志愿导师时，第一志愿导师只在【初筛确认】或【报名终止】环节，且存在 `first_choice_screening_submitted_at` 时可重新评分。
4. 第二志愿导师只在【初筛确认】或【报名终止】环节，且存在 `second_choice_screening_submitted_at` 时可重新评分。
5. 已进入【面试阶段】的记录一律禁止重新评分。
6. 禁止时统一提示：因为该学生已经到了面试阶段所以无法重新评分。
7. 重新评分成功后，目标记录必须回到【导师初筛】可评分状态。

为什么这样做：

1. 先冻结判定口径，后续后端判断、前端交互和测试才能对齐。

确认点：

1. 你确认【初筛确认可回退，面试阶段不可回退】的规则后，再进入实现。

### 第 2 步：补齐后端阶段判断与回退处理

怎么做：

1. 在现有【已提交】查询或管理服务链路中增加重新评分判断入口。
2. 依据学生当前业务阶段判断是否允许重新评分。
3. 对允许的记录执行状态回退，使其回到【导师初筛】环节。
4. 对不允许的记录返回统一错误提示。
5. 保证回退后相关字段、状态和列表刷新口径一致。

为什么这样做：

1. 重新评分的核心是状态控制，必须先在后端收口，否则前端无法保证业务正确性。

确认点：

1. 后端能准确区分可回退与不可回退场景，并返回明确结果。

### 第 3 步：在已提交列表增加操作入口

怎么做：

1. 将【查看】列改名为【操作】列。
2. 在该列中保留【查看详情】并新增【重新评分】。
3. 点击【重新评分】时先弹出确认提示，再发起后端请求。
4. 失败时展示【因为该学生已经到了面试阶段所以无法重新评分】。
5. 成功后刷新列表，让该记录从已提交状态中消失或更新为可重新评分状态，按业务口径处理。

为什么这样做：

1. 操作入口要清晰可见，且必须直接反映后台状态判定结果。

确认点：

1. 用户能从【已提交】列表直接完成重新评分动作。

### 第 4 步：补验证用例与构建检查

怎么做：

1. 补充接口测试，覆盖可回退与不可回退两类场景。
2. 补充前端点击【重新评分】的交互验证。
3. 确认列表刷新、错误提示、按钮可用性正常。
4. 完成前端构建或静态检查。

为什么这样做：

1. 这个需求涉及状态回退，必须用验证锁住边界行为。

确认点：

1. 测试与构建通过后，再进入文档同步。

### 第 5 步：同步文档与开发记录

怎么做：

1. 更新相关需求说明与开发计划。
2. 记录重新评分的判定边界与失败提示文案。
3. 若需要，再补充上线说明和回滚说明。

为什么这样做：

1. 重新评分属于状态回退能力，文档必须明确业务边界，避免后续误用。

确认点：

1. 文档与实现保持一致后，结束本轮。

## 7. 验收标准

1. 【已提交】列表中【查看】列已改为【操作】列。
2. 【操作】列中可以看到【重新评分】动作。
3. 目标记录处于【初筛确认】环节时，可成功回退到【导师初筛】。
4. 目标记录已到【面试阶段】时，重新评分被禁止并显示指定提示。
5. 【已提交】列表原有查询、分页、志愿、分数、结论和查看详情不受影响。

## 8. 风险与注意事项

1. 业务阶段判断必须以服务端为准，不能只靠前端按钮隐藏。
2. 回退后要同步刷新列表状态，否则用户会误以为操作失败或未生效。
3. 不要把【初筛确认】和【面试阶段】的判断写散到多个页面里，应该统一收口。
4. 错误提示文案要保持固定，避免不同页面出现不一致说法。

## 9. 待确认点

1. 回退成功后，列表里该记录是否需要立即从【已提交】消失，还是保留但状态变化后再由刷新重新拉取。
2. 【重新评分】是否需要增加二次确认弹窗。
3. 【操作】列里是否还需要保留【查看详情】并与【重新评分】并列展示。
4. 后端回退接口命名是否需要先统一。
