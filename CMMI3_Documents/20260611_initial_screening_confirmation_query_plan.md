# 初筛确认查询列表改造计划

## 背景

当前 `/recruitment/initial-screening-confirmation` 页面使用的是通用报名列表查询逻辑，查询条件、字段展示和筛选规则都和其他报名页面混在一起。

为了避免后续继续影响其他查询功能，本次只拆分【初筛确认】的查询列表能力，不修改确认、提交、状态流转等动作逻辑。

## 修改目标

1. 单独新增一个【初筛确认】查询服务文件。
2. 以 `backend/sql/初筛确认SQL脚本.sql` 为基础，形成专用列表查询。
3. 导师筛选改为使用 `app.first_choice` 或 `app.second_choice`。
4. 关键字搜索支持 `app.candidate_no` 和 `stu.full_name`。
5. 列表字段增加第一志愿分数、第二志愿分数。
6. 【初筛确认】页面隐藏申请状态筛选功能。

## 修改范围

- [backend/sql/初筛确认SQL脚本.sql](../backend/sql/%E5%88%9D%E7%AD%9B%E7%A1%AE%E8%AE%A4SQL%E8%84%9A%E6%9C%AC.sql)
- 新增一个独立的后端查询服务文件
- 需要时再补充一个独立的路由入口
- 前端只做【初筛确认】页面的查询接入和展示调整

## 修改步骤

### 第 1 步：把 SQL 脚本整理成可复用的查询模板

怎么做：

- 先把 `backend/sql/初筛确认SQL脚本.sql` 改成参数化查询模板。
- 保留基础条件：
  - `app.application_status = 'initial_screening_confirmation'`
  - `app.is_deleted = FALSE`
  - 第一/第二志愿分数满足初筛确认条件
  - 第一/第二志愿提交时间不为空
- 去掉写死的 `plan_id = 5`，改成入参。

为什么这样做：

- 这样后续新服务文件可以直接沿用同一套查询规则，避免 SQL 和代码逻辑分叉。

确认点：

- 这条 SQL 只能筛出初筛确认清单，不应再覆盖其他报名状态。

### 第 2 步：新增独立的初筛确认查询服务文件

怎么做：

- 新建一个只读查询服务文件，例如 `backend/app/services/initial_screening_confirmation_service.py`。
- 在这个文件里只实现列表查询和分页，不放确认、提交、流转相关逻辑。
- 服务内部直接封装【初筛确认】查询条件，避免再复用通用报名列表查询入口。

为什么这样做：

- 你明确要求“单独新增一个代码文件”，这样能把【初筛确认】的查询和其他功能物理隔离。

确认点：

- 新文件只负责查询列表，不包含任何动作接口。

### 第 3 步：按新需求改列表筛选条件

怎么做：

- 导师筛选改成 `app.first_choice` 或 `app.second_choice` 的匹配逻辑。
- 关键字搜索只保留 `app.candidate_no` 和 `stu.full_name`。
- 保留分页参数 `page`、`page_size`。

为什么这样做：

- 这样【初筛确认】页面的筛选语义才和业务一致，不再复用通用页面里偏报名管理的筛选方式。

确认点：

- 输入导师名后，能查到第一志愿或第二志愿匹配的记录。
- 输入报名号或学生名后，能查到对应记录。

### 第 4 步：补充列表返回字段

怎么做：

- 列表返回中增加：
  - `app.first_choice_screening_score`
  - `app.second_choice_screening_score`
- 前端展示规则保持简单：
  - 第一志愿分数为空时显示“等待初筛”
  - 第二志愿分数为空时留空

为什么这样做：

- 初筛确认页需要直接看到两志愿的确认依据，才能减少切页和二次查询。

确认点：

- 列表中能直接看到两个分数字段，且空值展示符合要求。

### 第 5 步：隐藏申请状态筛选

怎么做：

- 在【初筛确认】页面隐藏申请状态筛选控件。
- 该页面只保留与初筛确认直接相关的筛选项。

为什么这样做：

- 你要求这个页面只聚焦初筛确认，避免用户误以为还能在这里切换通用申请状态。

确认点：

- 【初筛确认】页面不再显示申请状态下拉框。

### 第 6 步：补最小验证用例

怎么做：

- 增加查询列表的测试，覆盖：
  - 导师按第一志愿匹配
  - 导师按第二志愿匹配
  - 报名号/学生名关键字搜索
  - 分数字段展示
  - 初筛确认页隐藏申请状态筛选

为什么这样做：

- 这次改动的核心风险是查询条件和展示字段走偏，测试要锁住查询语义。

确认点：

- 新增用例通过后，再进入下一轮调整。

## 执行顺序建议

1. 先新增独立查询服务文件。
2. 再接入新的查询接口。
3. 然后调整前端初筛确认页的字段和筛选项。
4. 最后补测试。

## 当前建议的最小落地方案

如果你想尽量保持改动边界清晰，我建议这次只做两件事：

1. 新增一个【初筛确认】只读查询服务文件。
2. 前端【初筛确认】页切换到这个新查询接口，并隐藏申请状态筛选。

这样可以把查询逻辑彻底和通用报名列表分开，后续如果还要扩展导出或统计，再单独加。

## 待你确认的点

- 是否按“单独新增查询服务文件”的方案执行。
- 是否允许新增一个专用查询路由。
- 是否先只做查询与展示，不碰任何动作接口。
