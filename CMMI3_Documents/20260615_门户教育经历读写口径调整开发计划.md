## 1. 背景

当前 `/portal/application` 的“教育经历”章节存在口径不清的问题。用户提出的最新规则是：

1. 已提交申请表以后，教育经历读取时以正式表 `dtlms_portal_application_education_experiences` 为主，如果草稿里存在更多信息，则允许补充显示。
2. 未提交申请表时，教育经历读取时以草稿为主，如果草稿缺少而正式表已有信息，则允许用正式表补充。
3. 最终提交申请表时，教育经历章节填写内容要同时写入草稿和正式表，也就是“提交 = 保存草稿 + 写正式表”。

本次开发的重点不是简单地“只看草稿”或“只看正式表”，而是把读取、保存、提交三条链路拆开，建立明确的主次来源和唯一回填入口，避免后续再出现“只显示最近一条”“提交后数据缺失”“草稿误回填正式表”等问题。

## 2. 目标

1. 明确 `/portal/application` 教育经历章节在未提交与已提交两种状态下的读取优先级。
2. 保证教育经历数据在页面展示时尽可能完整，正式表与草稿之间按规则互补。
3. 保证提交申请表时，教育经历章节内容同时落草稿与正式表。
4. 禁止在除“提交申请表”之外的任何路径中，将草稿反向回填到正式表。
5. 保持现有页面结构、接口风格与数据模型尽量稳定，避免引入不必要的范围扩张。

## 3. 当前现状判断

### 3.1 已有基础

1. 前端 `PortalApplicationV2Form.vue` 已具备教育经历数组编辑能力。
2. 前端 `PortalEducationSection.vue` 已按 `education_experiences` 数组展示数据。
3. 后端 `dtlms_portal_application_education_experiences` 已支持多条教育经历记录。
4. 后端 `application_draft` 结构中也已经存在 `education_experiences` 相关字段。

### 3.2 当前缺口

1. 读取链路中，草稿与正式表的补齐顺序与合并规则尚未严格按新口径统一。
2. 提交链路中，教育经历写入草稿和正式表的职责边界还需要再次收束。
3. 现有兼容逻辑里仍存在旧字段 `education_experience` 的回退路径，需要确认不会破坏新的主次来源规则。
4. 需要确认学生端、管理端、注册学生详情、招生详情等读取入口是否都遵循同一套教育经历口径。

## 4. 范围说明

本轮只做以下内容：

1. 调整 `/portal/application` 教育经历章节的读取优先级与补齐逻辑。
2. 调整提交申请表时教育经历的同步写入逻辑。
3. 调整必要的后端服务、schema、状态同步与前端回显逻辑。
4. 补充验证与文档。

本轮不做以下内容：

1. 不扩展教育经历之外的其他章节口径。
2. 不新增与本需求无关的字段或业务流程。
3. 不重构整个 portal 报名体系，只做教育经历链路的定向收敛。

## 5. 开发步骤

### 第 1 步：冻结读写边界与合并规则

怎么做：

1. 先确认教育经历的唯一正式来源是 `dtlms_portal_application_education_experiences`。
2. 明确草稿中的 `education_experiences` 仅作为未提交状态下的主来源和提交前的编辑载体。
3. 明确正式表只在提交申请表动作中接收草稿回填。
4. 明确旧字段 `education_experience` 只作为历史兼容读取来源，不作为新的主写入来源。

本步骤冻结后的规则：

1. 未提交时，页面优先读取草稿；草稿缺项时再用正式表补齐。
2. 已提交后，页面优先读取正式表；正式表缺项时再用草稿补齐。
3. 提交时，教育经历章节内容同时写入草稿与正式表。
4. 除提交动作外，禁止草稿反向回填正式表。

已确认的控制点：

1. `PortalApplicationV2Form.vue` 的初始化入口会优先取 `profile.application_draft.education_experiences`，并在草稿为空时才退回 `profile.education_experience` 的 legacy 解析。
2. `PortalEducationSection.vue` 只负责展示 `form.education_experiences` 数组，不负责来源判断。
3. `management_service_portal.py` 的草稿构造会把 `education_experiences` 写入 `application_draft`，提交时也会沿用同一份表单内容。
4. `postgres_state_store_sync.py` 当前会把 `application_draft.education_experiences` 写入正式表，因此后续必须把“只有提交才允许正式表回填”的边界收紧到提交动作本身。
5. `postgres_state_store_core.py` 与 `postgres_state_store_query_students.py` 仍存在 legacy 字段 `education_experience` 的兜底读取，需要在下一步收口时明确补齐顺序。

确认点：

1. 你确认上述规则后，再进入代码调整。

### 第 2 步：梳理读取链路

怎么做：

1. 排查 portal 学生详情、报名页面初始化、注册学生详情、招生工作台详情等读取入口。
2. 识别当前哪些入口直接读草稿，哪些入口直接读正式表，哪些入口还在依赖旧字段 `education_experience`。
3. 统一建立“主来源 + 补充来源”的合并顺序。
4. 避免草稿和正式表互相覆盖，特别是提交后的历史数据展示。

当前读取链路的初步结论：

1. 门户详情返回到前端时，`PortalStudentRecord.populate_structured_sections` 会优先使用 `application_draft.education_experiences`，只有草稿不存在时才从 legacy 字段 `education_experience` 解析，并不会自动从正式表 `dtlms_portal_application_education_experiences` 补齐。
2. `PortalApplicationV2Form.applyProfile()` 接到门户详情后，回显优先使用 `profile.application_draft.education_experiences`，其后只退回 `profile.education_experience` 的 legacy 解析，说明当前前端没有单独读取正式表作为补齐来源。
3. `postgres_state_store_core._derive_portal_application_draft()` 与 `_merge_portal_application_draft()` 仍以草稿和 legacy 学生字段为核心来源，读链路并未按“已提交优先正式表、未提交优先草稿”的状态口径分流。
4. `postgres_state_store_query_students.py` 和 `postgres_state_store_query_recruitment.py` 在学生/招生详情查询时会直接读取正式表 `dtlms_portal_application_education_experiences`，但这些入口属于管理与招生详情，不是 `/portal/application` 页面本身的回显主链路。
5. `schemas/portal.py` 中的 `populate_structured_sections()` 与 `_populate_application_draft_fallbacks()` 仍以 `education_experience` legacy 字段补齐草稿，没有把正式表作为草稿回填的补充来源纳入当前模型层。
6. `management_service_portal.py` 的草稿保存与提交 payload 已携带 `education_experiences` 数组，但读取入口如果只依赖 `application_draft`，仍会继续沿用草稿优先的旧路径。

为什么这样做：

1. 先把读取链路收口，才能解释为什么页面只能看到最近一条，避免只修一个入口后其他入口继续偏离。

确认点：

1. 各入口读取结果在未提交与已提交场景下都符合新口径。

### 第 3 步：调整提交链路

怎么做：

1. 在提交申请表动作中，先按当前表单内容保存草稿。
2. 再把同一份教育经历内容写入正式表 `dtlms_portal_application_education_experiences`。
3. 确保正式表写入只发生在提交动作，不在保存草稿、普通读取、详情回显、同步加载等路径触发。
4. 保留必要的事务一致性，避免草稿已更新但正式表写入失败时出现双态不一致。

已完成的实现结果：

1. `submit_portal_application()` 现在会先调用 `self._persist_portal_student_change(student, None)` 保存草稿，再调用 `_persist_portal_application_submission(...)` 写正式表。
2. `_persist_portal_application_submission()` 新增 `persist_portal_student` 参数，提交路径明确传入 `False`，避免同步层再次无条件重写 portal 学生主表。
3. `sync_portal_application_submission()` 新增 `persist_portal_student` 开关，提交时仅在显式允许时才执行 portal 学生主表重建，保证草稿回填正式表只发生在提交链路。
4. `sync_portal_student()` 继续只负责草稿与学生主表同步，不承担正式表回填职责。

为什么这样做：

1. 你的要求是“点击提交 = 保存草稿 + 写正式表”，这需要提交动作具备明确的双写职责。

确认点：

1. 提交后，草稿与正式表中的教育经历内容一致，且正式表有完整记录。

### 第 4 步：修正前端回显与校验

怎么做：

1. 调整 `PortalApplicationV2Form.vue` 的初始化逻辑，让教育经历的回显按状态走主次合并。
2. 确保 `PortalEducationSection.vue` 仍然只负责展示数组，不承担来源判断。
3. 校验“未提交优先草稿”“已提交优先正式表”的结果是否能正确映射到表单。
4. 保持教育经历章节新增、删除、排序、附件展示逻辑不被破坏。

为什么这样做：

1. 读取规则最终是要落到页面展示上，前端回显需要跟后端口径一致。

确认点：

1. 页面不会再出现只展示最近一条的误差。

已完成的实现结果：

1. `PortalApplicationV2Form.vue` 的教育经历回显已按提交状态拆分主次来源，未提交时优先草稿并用正式表补齐，已提交时优先正式表并用草稿补齐。
2. `PortalStudentRecord` 已补充正式表教育经历数组字段，前端可以直接消费统一的结构化数据。
3. `postgres_state_store_query_students.py` 在门户学生详情查询中补出了正式表教育经历数组，保证 `/portal/application` 的回显链路有可用的正式表来源。
4. `PortalEducationSection.vue` 未做来源判断，仍保持纯展示职责。

### 第 5 步：修正后端数据组装与同步

怎么做：

1. 排查后端报名详情、学生详情、门户详情、管理端详情的组装逻辑。
2. 确认 `application_draft.education_experiences` 与正式表 `dtlms_portal_application_education_experiences` 的合并顺序。
3. 确认历史兼容字段 `education_experience` 只做补充兼容，不覆盖新数组口径。
4. 若同步层存在把草稿写入正式表的非提交路径，需要收口或加条件保护。

为什么这样做：

1. 前端只是展示层，真正的数据边界必须在后端统一收住。

确认点：

1. 所有后端读取入口都不会在非提交场景下把草稿误写回正式表。

已完成的实现结果：

1. `schemas/portal.py` 的 `PortalStudentRecord` 已补充 `education_experiences` 字段，并在门户详情模型归一化时优先消费结构化教育经历。
2. `postgres_state_store_query_students.py` 在学生详情查询中已经把正式表教育经历数组写回顶层字段，同时保留 legacy `education_experience` 兼容回填。

## 6. 验收标准

1. 未提交申请表时，教育经历按草稿优先展示，草稿缺项可由正式表补齐。
2. 已提交申请表后，教育经历按正式表优先展示，正式表缺项可由草稿补齐。
3. 提交申请表时，教育经历内容会同时写入草稿和正式表。
4. 除提交动作外，不存在草稿回填正式表的其他路径。
5. `/portal/application` 教育经历章节可正确展示多条记录，不再只看见最近一条。

## 7. 风险与注意事项

1. 读取合并规则要避免重复条目或错序展示，特别是草稿和正式表都存在同类记录时。
2. 提交双写要注意一致性，不能出现草稿更新成功但正式表失败的半成功状态。
3. 兼容字段 `education_experience` 仍可能影响旧数据回显，必须明确它只做补充，不做主写。
4. 这次调整涉及多个入口，不能只改一个页面而忽略后端详情和同步层。
