## 一、背景与目标

### 1.1 现状

`dtlms_operation_logs` 表已经包含以下列（见 `backend/app/models/system.py` 的 `OperationLog`）：

| 列 | 类型 | 现状 |
| --- | --- | --- |
| `operator_username` | varchar(64) NOT NULL | ✅ 由中间件兜底时通过 `decode_token` 解析 |
| `operator_role` | varchar(64) NOT NULL | ⚠️ SQL 层硬编码为 `"runtime_seed"`（见 `_sync_operation_log_in_tx`），未真正实现 |
| `module_name` | varchar(64) NOT NULL | ✅ 中间件从 URL 第一段推断或业务描述器指定 |
| `entity_name` | varchar(64) NOT NULL | ✅ 同上 |
| `entity_id` | varchar(64) NOT NULL | ✅ URL 末段（部分接口仍为 `-`） |
| `action` | varchar(32) NOT NULL | ✅ 中文：`新增 / 编辑 / 删除 / 操作` |
| `old_value` | JSONB | ❌ **始终为 NULL**（`_sync_operation_log_in_tx` 写死 `NULL`） |
| `new_value` | JSONB | ⚠️ 仅当业务手工 `_record_operation` 并经 store 持久化时才写 |
| `request_ip` | varchar(64) | ❌ **从不写入** |
| `result` | varchar(32) NOT NULL | ✅ `success / failed`，但失败原因丢失 |
| `created_at / updated_at` | timestamp | ✅ |

前端 `OperationLogRecord` 只暴露了 `summary` 文本字段，**不返回 `old_value / new_value / request_ip / 错误详情`**。

### 1.2 痛点

1. **操作缺详情**：审计看到 `编辑 dict-types id=1 - PUT /api/v1/system/dict-types/1`，但不知道"什么字段改了、改成什么"。
2. **失败信息缺失**：后端返回 `400 Dict value already exists`、`404 Dict type not found`、`500 Internal Server Error` 时，操作日志里只能看到 `result=failed`，分不清是哪类失败。
3. **不可定位客户端**：日志没有 `request_ip`，无法做溯源。
4. **业务手工记录路径也不完整**：`management_service_recruitment.py` 等手动记录的 `operation_log` 字典没有携带 `old_value / new_value / request_ip`。

### 1.3 目标

| ID | 目标 | 验收标准 |
| --- | --- | --- |
| G1 | 每条操作日志携带请求 payload 快照 | 所有 `result=success` 的写操作日志，`new_value` 字段为非空 JSON |
| G2 | 编辑类操作可看到修改前快照 | `PUT` 接口日志 `old_value` 与 `new_value` 字段值不同且与数据库变更一致 |
| G3 | 失败操作日志带可读错误详情 | `result=failed` 的日志 `error_detail` 字段含 `status_code` + `exception_type` + 可读消息 |
| G4 | 所有日志可定位来源 IP | `request_ip` 列非空（除非走代理仍可解析） |
| G5 | 敏感字段不落库 | `password*` `token*` `secret*` `*_hash` `refresh_token` 等入库时为 `***` |
| G6 | 不破坏现有契约 | 现有 `test_backoffice_operation_audit.py` 3/3 通过；"业务手工记录则中间件不重复"契约仍生效 |
| G7 | 大体量 body 不撑爆库 | 请求 body >32KB 时截断 + `truncated=true` 标记 |
| G8 | 前端可消费 | `OperationLogListResponse` 暴露新字段；详情抽屉有专门渲染 |

## 二、关键设计抉择

| 决策点 | 选择 | 理由 |
| --- | --- | --- |
| 敏感字段脱敏 | 黑名单替换 `password*` `token*` `secret*` `*_hash` `refresh_token` 为 `***` | 合规最小集，避免密码/Token 落库 |
| body 体积上限 | 32KB；超过则截断 + 标记 `truncated=true` | 防止 JSONB 单行过大影响查询性能 |
| `old_value` 来源 | 业务手工记录时由调用方传；中间件兜底路径对字典写接口读 `list_*` 取全量 | 中间件路径取全表成本可控（百行级）；其它业务手工记录覆盖 |
| 失败 traceback | 记录 `exception_type` + `detail/str(exc)` + traceback 前 20 行 frame + 截断到 1KB | 调试 500 必需，但避免日志爆列 |
| `request.body()` 时机 | 在中间件里调用一次并缓存到 `request.scope["_body_cache"]`，路由层通过 `await request.body()` 复用 | Starlette 标准做法，对现有路由零侵入 |
| 失败操作计 1 条 | 单条日志含 `error_detail`，不再额外兜底 | 保持"业务手工记录则中间件不重复"的现有契约 |
| 上下文传递 | 新增 `app/core/operation_audit_context.py` 中的 `set/get` ContextVar 字典，支持 `payload / old_value / new_value / request_ip / status_code / error_detail / elapsed_ms` | 与项目现有 `_manual_operation_log_count` ContextVar 同模块扩展 |
| 异步写日志 | 保持同步，事务内随主操作一起 commit | 沿用 `_persist_operation_log` 通过 `sync_operation_log` 写 |
| 跨实例 trace id | 不引入 | 项目无分布式 trace 系统 |

## 四、技术方案

### 4.1 数据流（成功路径）

```
HTTP 请求
  │
  ▼
record_backoffice_operation_audit (中间件)
  │  ├─ request.body() → 缓存到 scope["_body_cache"]
  │  ├─ 解析 request_ip（X-Forwarded-For → X-Real-IP → request.client.host）
  │  ├─ 进入业务处理
  │  │    └─ 业务函数可选调用 store.record_operation_event(..., old_value, new_value, ...)
  │  │         └─ 写 _audit_context ContextVar（payload/ip/error...）
  │  │         └─ 调 _record_operation → mark_manual_operation_log()
  │  │         └─ 调 _persist_operation_log → store.sync_operation_log
  │  │              └─ SQL: INSERT/UPSERT dtlms_operation_logs
  │  └─ 退出时检查 _counters 是否增加；如未增加则兜底
  │       └─ 兜底时使用 request.body() 缓存作为 new_value
  │       └─ 通过 _resolve_business_audit_descriptor 推断 module/entity/action
  ▼
HTTP 响应
```

### 4.2 数据流（失败路径）

```
HTTP 请求
  │
  ▼
record_backoffice_operation_audit
  │  进入业务 → 抛 HTTPException(400, "Dict value already exists")
  │  或抛 RequestValidationError（422）
  │  或未捕获异常（500）
  ▼
中间件捕获 raised_exc
  │  ├─ 提取 status_code（响应 status_code 或 HTTPException.status_code）
  │  ├─ 提取 exception_type / detail / errors()
  │  ├─ 取 traceback.format_exc(limit=20) 截断到 1KB
  │  └─ 写 error_detail ContextVar
  │  └─ record_operation_event(... result="failed" error_detail=...)
  ▼
日志入库
```

### 4.4 关键 SQL 改造

```sql
-- _sync_operation_log_in_tx（修改后）
INSERT INTO dtlms_operation_logs (
    id, operator_username, operator_role, module_name, entity_name, entity_id,
    action, old_value, new_value, request_ip, status_code, elapsed_ms,
    error_detail, result, created_at, updated_at
) VALUES (%s, %s, %s, %s, %s, %s, %s, %s::jsonb, %s::jsonb, %s, %s, %s, %s::jsonb, %s, %s, %s)
ON CONFLICT (id) DO UPDATE SET
    operator_username = EXCLUDED.operator_username,
    module_name       = EXCLUDED.module_name,
    entity_name       = EXCLUDED.entity_name,
    entity_id         = EXCLUDED.entity_id,
    action            = EXCLUDED.action,
    old_value         = EXCLUDED.old_value,
    new_value         = EXCLUDED.new_value,
    request_ip        = EXCLUDED.request_ip,
    status_code       = EXCLUDED.status_code,
    elapsed_ms        = EXCLUDED.elapsed_ms,
    error_detail      = EXCLUDED.error_detail,
    result            = EXCLUDED.result,
    created_at        = EXCLUDED.created_at,
    updated_at        = EXCLUDED.updated_at;
```

> **注意**：`old_value` 由业务调用方传入（如有）；中间件兜底时若未传则 `NULL`。这不是新约束，与现状一致。

### 4.5 脱敏规则

```python
# app/services/management_service_core.py 内的 _sanitize_payload
_SENSITIVE_KEYS = {"password", "passwd", "secret", "token", "access_token",
                   "refresh_token", "authorization", "api_key", "*_hash", "*_secret"}
_MAX_BODY_BYTES = 32 * 1024
_MAX_ERROR_DETAIL_BYTES = 1024
_TRACEBACK_FRAME_LIMIT = 20
```

- 命中黑名单（大小写不敏感、前缀/后缀通配）的 value 替换为 `"***"`
- body > 32KB 截断到 32KB 并加 `"_truncated": true` 标记
- error_detail traceback 限制 frame 数 + 总字节数

### 4.6 `request_ip` 解析顺序

```
X-Forwarded-For (逗号分隔取第一个) → X-Real-IP → request.client.host
```

实现位于 `_resolve_request_ip(request: Request) -> str | None`。

## 八、风险与回滚

| 风险 | 等级 | 缓解 | 回滚 |
| --- | --- | --- | --- |
| 中间件 body 缓存与现有路由不兼容 | 中 | 用 `request.scope["_body_cache"]` 复用 starlette 标准做法 | 移除 body 缓存，仅写 IP / error |
| 业务手工记录路径漏改导致 old_value 全空 | 低 | 步骤 4 一次性扫完所有 `_record_operation` 调用点 | 单独关闭步骤 4，保留中间件兜底 |
| 大体量 body 截断导致审计信息丢失 | 低 | 保留 `truncated=true` 标记 + summary 中提示"body 过大已截断" | 调高 `MAX_BODY_BYTES` |
| SQL 层 INSERT 列数增加导致旧调用方不兼容 | 中 | 所有新增列允许 NULL；旧调用不传则 `NULL` | 无需回滚（向后兼容） |
| 错误详情泄露敏感信息（异常 message 含 SQL） | 中 | `_sanitize_error_detail` 对 SQL 关键字/连接串脱敏 | 关闭 error_detail 入库，仅记 status_code |
| 性能：每写操作多 1 次 DB 读（兜底拉 old_value） | 低 | 仅字典写接口兜底拉；其它接口走业务路径 | 兜底路径不写 old_value |
